# 更新后继续原任务

更新应保留原任务、计划、事件、模型配置和素材引用。重新打开 Codex 以刷新 Skills，不等于重新创建媒体任务；继续使用原 session ID 和请求键。

安装器把数据位置独立记录在状态目录的 `data-binding.json`，运行端口和进程记在 `runtime.json` 与备份登记中。换源码目录或端口不会改变数据绑定。已有数据库不可访问、配置改指另一数据库、或发现多个含任务的旧库时，启动会给出可恢复的错误，不会用新空库冒充更新成功。

升级前使用 SQLite 在线备份接口保留数据库，并在本机备份配置。备份位于状态目录的 `backups/`，最新位置记录在 `upgrade-backup.json`。这些文件可能包含私人项目和模型凭据，应留在本机，不能上传 Git 或粘贴到公开对话。启动后会核对数据库身份及主要任务记录数量；发现减少不确认升级成功。备份保留，程序不会自动覆盖原数据库或删除旧备份。

## 任务突然不见时

先让 Codex 运行只读诊断，保留当前实例和文件：

```text
node <插件目录>/scripts/runtime-launcher.mjs doctor --project-root <源码目录>
```

诊断返回登记、数据绑定和候选数据库的路径、指纹、记录数量，不输出任务内容和 Key。如有明确旧运行目录，可追加 `--search-root <旧后台数据根>` 检查。不要根据两个空任务列表断言旧数据已删除；先核对旧源码的 `backend-node`、原安装状态目录、配置中的数据库路径和已有备份。

没有已有数据绑定且定位到唯一旧库时，启动器自动采用它。多库时比较原 session ID、任务记录和素材引用，再显式指定旧 `--runtime-root`；不能盲目挑最近文件或新空库。已有绑定需要恢复原路径或从备份按原路径恢复，恢复前保留当前数据库及 WAL/SHM 文件；不要把原始SQLite文件在运行中直接覆盖或把备份拷入公开源码。确实没有原库和备份时，说明不可恢复的证据范围，不伪造任务历史。

## Skills 不显示时

安装器会把 Skills 和 CLI 依赖复制到固定的本机版本目录，保留相对模块结构，再建立 Codex 可发现的入口。Windows 插件安装分支也安装独立 Skills；默认兼容 `.agents/skills` 和 Codex 配置目录的 `skills`，自定义路径按安装参数处理。`skill-installation.json` 可回读入口、目标、内容版本和 MCP 文件位置。安装器不覆盖无关的同名自定义 Skill。

插件缓存版本随安装内容变化。当前 Codex 任务若尚未刷新工具，直接读安装副本的 `SKILL.md` 并使用 CLI 继续原任务；新开 Codex 任务或重启仅用于刷新工具发现，原工作流数据库和 session ID 仍保持不变。

## 同时出现多个后台时

所有正式入口复用同一安装状态；直接执行后端入口也会进入统一启动器。同一数据库在迁移、任务恢复和外部轮询之前取得进程排他锁。重复启动复用已有后台，不再因为端口忙而针对同库另开一个后台。

旧版本已留下的重复后台，启动器在常用旧端口及登记地址检查数据库指纹，核对 PID 与运行时身份后，只整理空闲的同库重复实例。仍在执行的任务、无法核对身份的进程和显式隔离的其他数据库保持不动，返回具体原因；不会仅因进程叫 `node.exe` 就终止它。开发和验收使用独立 `YINZI_WORKFLOW_RUNTIME_DIR`，需要直接运行隔离后端时显式设置 `YINZI_WORKFLOW_ISOLATED=1`。
