# 本地视频发布验收记录

本记录把本地视频候选的“能运行”“能恢复”和“适合交付”分开。它不把一次模型样片升级成通用质量承诺。

## 当前结论

- H3 Turbo8 的 Windows x64 + NVIDIA 路线已经有真实采样、有限值检查、断点恢复和独立解码路径。
- 2026-09-22 又完成四个新增 Turbo8 场景的独立解码与正常速度用途审片：电商粗 B-roll、动漫 blocking、雨夜街景气氛和黑底粒子层。它们分别保留在实验目录的 MP4 与接触表中，结论只适用于对应镜头类型。
- 采样完成只表示 `video-latent.pt` 已保存；必须继续独立解码、导出、ffprobe 检查和正常速度审片，才能称为有 MP4。
- GPU 画质不在 CI 中自动验收。每个实际任务仍要检查身份、构图、动作顺序、接触关系、连续性、用途和音频。
- 本批四条新增 MP4 均为 `audio:none`，因此技术解码通过不代表原生音频可用；它们不是完整 MV 质量保证。
- 本轮独立代码审查确认 Windows CPU 合同测试通过；Linux 进程生命周期、共享目录并发修改和跨硬件速度仍是未知。

## 合并前修复

1. 父执行器退出时，runner 先调用 `stop_tree`，只终止自己拥有的推理树。
2. 恢复解码在 `torch.load` 前重新核对 latent/audio 文件 SHA-256，恢复目录在任务期间必须由单一任务独占。
3. 将静音路线的边界异常命名为 `SamplingCompleteDecodeRequired`，明确采样完成但解码尚未完成。
4. 文字编码缓存键加入固定文字编码器的 manifest SHA-256，避免同名权重被替换后错误复用。
5. 已有隔离环境的导入探针按 `models.minimax_h3.pipeline` 包身份加载，修复相对导入失败；解析独立完成标记，允许依赖库输出提示。真实环境返回 `ready`，安装/下载回归共 24 项通过。此结果不代表全新安装、所有硬件或艺术质量通过。

## 发布后恢复交接修正

2026-09-22 回查发现：新生成任务采样完成后写出了 `recovery.json`，但转入独立解码时没有把新 checkpoint 的 SHA-256 传入请求，触发 `Recovery hash missing for video-latent.pt`。已改为从刚写出的清单传递校验值，保留解码器的缺失/变更拒绝规则；已有文件恢复的 schema 和参数不变。

新增 CPU 回归实际调用 runner 和解码器校验函数，覆盖新采样到解码、文件改变时拒绝导出、解码失败后复用 latent 不重采样、像素恢复不加载模型或占用 GPU，以及缺失校验值拒绝。修复前五项测试中四项失败，修复后五项全部通过。模型计算和导出在该套测试中使用替身，因此它证明阶段交接合同，不代表新增一次 GPU 成片或画质验收。此前实验用独立兼容解码器生成的样片不能替代这条产品路径的回归。

## 证据边界

Windows 实测主机为 RTX 2070 SUPER 8 GiB、Ryzen 5 3600X、48 GiB RAM；H3 Turbo8 的 832×480、107 帧、24 fps 近景样本约 23 分钟。该数字只描述观测主机和该样本，不是其它显卡、长片段或电影级动作的保证。H3 与 WanGP 的社区许可分别记录，不能合并成 Apache 或商用保证。

四个新增 benchmark latent 使用旧版 `{latent, config}` 包装，独立兼容解码器可以读取并生成证据，但它们不是正式 `local.video.recover` 的输入。正式恢复仍必须有带 fingerprint、parameters、prompt、source revision 和 hashes 的 `recovery.json`。这条兼容性边界已写入恢复 Skill，避免把旧实验结果伪装成产品恢复完成。
